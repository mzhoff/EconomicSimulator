# Phase 1: TokBeri Deterministic Foundation

## 1. Цель

Адаптировать текущий EconomicSimulator под реальную экономику TokBeri и
получить локальный инструмент, с помощью которого можно:

- менять допущения;
- пересчитывать экономику станции;
- сравнивать базовый и альтернативные сценарии;
- видеть влияние драйверов на выбранную ключевую метрику;
- находить безубыточность и требуемую загрузку;
- сохранять и переносить модель без потери формул.

Этап должен дать практическую пользу до появления time-series и импорта
событий.

## 2. Основное ограничение

Phase 1 рассчитывает один выбранный период, по умолчанию месяц.

Типы `Stock / Flow / Rate / Event` уже присутствуют в схеме и проверках, но:

- история Stock по периодам пока не моделируется;
- Event можно описать, но нельзя загружать пачкой;
- автоматическая агрегация событий не реализуется;
- рекуррентные формулы не реализуются.

Это сознательное ограничение, а не архитектурный тупик.

## 3. Что не входит

- франчайзинговая экономика как доверенный результат;
- HQ-модель;
- налоги без подтверждённой налоговой схемы;
- backend и авторизация;
- интеграция с TokBeri API;
- импорт CSV/XLSX событий;
- stock-flow timeline;
- Monte Carlo;
- AI;
- совместная работа.

## 4. Экономический контракт TokBeri

### North Star по умолчанию

Пока налоги не заданы, метрика называется:

```text
Прибыль до налогов
```

Пользователь может выбрать другую North Star, например:

- денежный вклад станции;
- срок окупаемости;
- прибыль сети;
- выручку;
- число успешных аренд.

### Денежные результаты

```text
rental_revenue
  = successful_rentals × average_check

cash_contribution
  = rental_revenue
  - venue_commission
  - acquiring
  - net_loss_cost
  - battery_wear
  - sim
  - maintenance
  - rebalancing
  - other_cash_opex

profit_before_tax
  = cash_contribution
  - station_depreciation

payback_months
  = capex / positive_cash_contribution
```

CAPEX не вычитается повторно через амортизацию при расчёте окупаемости.

### Выручка

Выручка строится только на успешных арендных списаниях.

Не включаются автоматически:

- депозит;
- неуспешная попытка оплаты;
- временный hold;
- начисление за потерю без подтверждённого платежа.

Возмещение за потерянное устройство показывается отдельным потоком.

### Потери

Первая версия поддерживает два режима:

1. упрощённый сценарный резерв;
2. событийная формула, когда известны lost units и recovered amount.

Предпочтительная формула:

```text
net_loss_cost
  = lost_units × replacement_cost
  + loss_handling_cost
  - recovered_lost_charge
```

### Износ

```text
battery_wear_cost
  = completed_turnovers
  / useful_cycles
  × replacement_cost
```

`useful_cycles` остаётся допущением и может включать заводской ресурс плюс
продление после технической проверки.

### Capacity

В Phase 1 не моделируется почасовое движение батарей, но вводятся guardrails:

- число батарей целое;
- занятые слоты не превышают общее количество;
- должен оставаться заданный минимум свободных слотов;
- расчётные аренды не должны молча превышать заданную операционную capacity;
- ограничение показывает warning, а не скрыто уменьшает спрос.

## 5. Стартовые сценарии

Набор сценариев:

| Сценарий | Аренд на станцию в день |
|---|---:|
| Weak | 0,3–0,5 |
| Base | 1–2 |
| Good | 3–5 |
| Hotspot | 10+ |

Дополнительно сценарий может переопределять:

- тип станции;
- количество батарей;
- тарифный микс;
- комиссию площадке;
- acquiring;
- loss rate;
- maintenance;
- uptime/capacity factor;
- CAPEX.

Сценарий хранит только отличия от baseline.

## 6. Обязательные метрики шаблона

### Спрос и использование

- потенциальный спрос;
- операционная capacity;
- фактические/моделируемые успешные аренды;
- аренды на станцию в день;
- тарифный микс;
- средний чек.

### Выручка

- арендная выручка;
- взысканное возмещение за потерянные устройства;
- общий денежный inflow с раздельным составом.

### Переменные расходы

- комиссия площадке;
- acquiring;
- потери;
- износ батарей;
- переменная логистика/ребалансировка.

### Постоянные расходы

- SIM;
- обслуживание;
- прочие расходы станции;
- амортизация.

### CAPEX

- станция;
- целое количество батарей;
- доставка;
- монтаж;
- стартовый запас;
- итоговый CAPEX.

### Результаты

- cash contribution;
- прибыль до налогов;
- payback;
- break-even rentals/day;
- target rentals/day для payback 12 и 24 месяца.

## 8. План реализации

### Pre-flight. Безопасная история изменений

Сейчас папка EconomicSimulator не является Git-репозиторием. Перед изменением
функционального кода, после отдельного подтверждения пользователя:

- инициализировать Git прямо в текущей папке;
- проверить `.gitignore`;
- исключить `node_modules`, временные файлы и локальные секреты;
- зафиксировать исходный прототип отдельным baseline-коммитом;
- не создавать соседнюю копию, worktree или GitHub remote без прямой команды.

Локальный Git не означает деплой или публикацию на GitHub. Он нужен как
восстанавливаемая история изменений.

### Workstream A. Зафиксировать эталонные кейсы

- перенести доверенные входные данные из Numbers в fixture;
- франшизу и HQ пометить как excluded;
- сохранить несколько контрольных сценариев;
- отдельно зафиксировать известные конфликты тарифа и депозита;
- определить допустимую погрешность расчётов.

Результат: тестовые примеры существуют до переписывания движка.

### Workstream B. Сериализуемое ядро

- создать schema v1;
- отделить core от React;
- заменить function closures на AST;
- получать dependencies из AST;
- реализовать топологический расчёт;
- возвращать явные ошибки вместо нулей;
- добавить проверку циклов на всём графе.

Результат: модель можно посчитать из чистого JSON.

### Workstream C. Типы и единицы

- добавить behavior;
- добавить структурированные units;
- добавить time basis и grain;
- проверить `+`, `-`, `*`, `/`;
- запретить Event в обычной арифметике;
- добавить понятные тексты ошибок;
- покрыть правила unit-тестами.

Результат: движок блокирует экономически бессмысленные формулы.

### Workstream D. TokBeri template

- заменить SaaS-метрики в стартовой модели;
- построить дерево прибыли станции;
- добавить cash contribution и корректный payback;
- добавить износ и event-based loss cost;
- сделать North Star выбираемой;
- добавить Weak/Base/Good/Hotspot.

Результат: при запуске пользователь видит прикладную модель TokBeri.

### Workstream E. Сценарии и анализ

- baseline + overrides;
- сравнение сценария с базой;
- относительный шок `+N%`;
- абсолютный шок `+N` и `+N percentage points`;
- sensitivity до выбранной North Star;
- threshold solver;
- явное отображение guardrails.

Результат: продукт отвечает на what-if и threshold-вопросы.

### Workstream F. Сохранение и переносимость

- autosave с debounce;
- localStorage;
- хранение последней валидной версии;
- backup перед миграцией;
- JSON export;
- безопасный JSON import;
- сохранение viewport отдельно от расчётной модели;
- round-trip тест.

Результат: закрытие браузера и перенос файла не уничтожают работу.

### Workstream G. Canvas integration

- сохранить текущий внешний вид;
- перенести проверенные механики navigation/selection из Image Production;
- pan средней кнопкой;
- zoom к курсору;
- box selection;
- Shift multi-select;
- group drag;
- context menu;
- undo/redo;
- запрет расчётного цикла в момент соединения.

Результат: новый engine работает под привычным редактором.

## 10. Критерии готовности

Phase 1 завершена, когда выполняются все условия.

### Расчёт

- одна модель полностью представлена JSON;
- после загрузки JSON результаты совпадают;
- цикл невозможно сохранить или импортировать;
- несовместимые единицы блокируют формулу;
- ошибка не превращается в ноль;
- payback считается через cash contribution;
- износ батарей влияет на экономику;
- количество батарей всегда целое.

### TokBeri

- стартовый шаблон не содержит SaaS-заглушек;
- Weak/Base/Good/Hotspot пересчитываются;
- тариф имеет версию и provenance;
- депозит не смешивается с выручкой;
- франшиза и HQ не показываются как доверенный результат;
- North Star можно поменять.

### What-if

- доступны относительный и абсолютный шоки;
- виден downstream impact;
- рассчитывается break-even;
- рассчитывается требуемая загрузка для payback 12/24 месяца;
- сценарий сравнивается с baseline.

### Надёжность

- autosave восстанавливает последнюю модель;
- невалидный импорт не уничтожает текущую модель;
- export/import сохраняет формулы, сценарии и позиции;
- миграция создаёт backup;
- production-сборка проходит;
- основные расчёты покрыты автоматическими тестами.

### UX

- дизайн визуально остаётся узнаваемым;
- pan/zoom/selection работают предсказуемо;
- ошибка объясняется простым языком;
- пользователь видит источник и статус ключевого допущения;
- базовый сценарий можно изменить без знания кода.

## 11. Вопросы, которые не блокируют начало

Эти значения можно хранить как версионированные допущения:

- окончательный тариф;
- депозит;
- точная стоимость логистики;
- стоимость обслуживания;
- размер резерва на потери;
- полезный ресурс батареи;
- capacity factor.

Их расхождение не должно тормозить engine. Напротив, продукт должен позволить
сравнить версии и показать влияние каждой.

## 12. Первый практический backlog

Порядок первых задач:

1. После подтверждения создать локальную Git-историю и baseline-коммит.
2. Создать тестовый JSON базовой 6-слотовой станции.
3. Написать эталонные тесты текущего и исправленного расчёта.
4. Описать schema v1 TypeScript-типами и runtime-валидацией.
5. Реализовать минимальный AST.
6. Реализовать unit inference.
7. Реализовать строгий DAG evaluator.
8. Собрать TokBeri template поверх нового core.
9. Подключить template к существующему интерфейсу.
10. Добавить сохранение и import/export.
11. Добавить сценарии, sensitivity и threshold.
12. Перенести Canvas-механики.
13. Провести end-to-end проверку пользовательского сценария.

После создания безопасной истории первыми инженерными задачами должны быть не
переделка Canvas, а эталонная модель, тесты и сериализуемая схема. Они зададут
фундамент всем последующим функциям.
