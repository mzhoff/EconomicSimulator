# Продуктовый и технический roadmap

## 1. Видение

EconomicSimulator — локальная рабочая среда продукт-менеджера для:

- моделирования экономики продукта;
- построения дерева драйверов;
- проверки what-if сценариев;
- поиска безубыточности и критических значений;
- оценки чувствительности выбранной North Star;
- сравнения допущений с фактическими данными;
- приоритизации продуктовых и операционных решений.

Ценность продукта не в красивом графе как таковом. Ценность возникает, когда
граф:

- имеет проверяемый экономический смысл;
- пересчитывается без ручных ошибок;
- показывает происхождение значений;
- объясняет, почему изменилась ключевая метрика;
- помогает выбрать действие.

## 2. Основные принципы

### От простого к сложному

Новая математическая возможность появляется только после того, как предыдущий
уровень проверен на TokBeri.

### Сначала детерминированная модель

Monte Carlo, AI и сложная динамика не имеют смысла, пока обычная формула прибыли
не разделяет CAPEX, cash flow, амортизацию и потери.

### Canvas не является источником истины

Источник истины — сериализуемая предметная модель. Canvas показывает и
редактирует её.

### Факт не смешивается с допущением

Пользователь всегда видит, что пришло из данных, что задано вручную и что
переопределено сценарием.

### Ошибка должна быть видимой

Цикл, несовместимые единицы, отсутствующее значение или неверный импорт
останавливают затронутый расчёт и объясняются пользователю. Движок не заменяет
ошибку нулём.

### Текущий дизайн сохраняется

Новая архитектура внедряется под существующий интерфейс. Полный редизайн не
является самостоятельной задачей.

## 3. Целевые пользовательские сценарии

### Сценарий A. Построить модель

1. Создать модель из шаблона или пустого Canvas.
2. Добавить входные и расчётные метрики.
3. Задать формулы.
4. Получить предупреждения о несовместимых типах и циклах.
5. Выбрать North Star.

### Сценарий B. Провести what-if

1. Создать сценарий от baseline.
2. Изменить несколько допущений.
3. Сравнить результат с базой.
4. Посмотреть вклад каждого изменения.
5. Сохранить сценарий для дальнейшего сравнения.

### Сценарий C. Найти критическое значение

1. Выбрать управляемый параметр.
2. Задать условие для целевой метрики.
3. Получить минимальное или максимальное значение параметра.

Пример:

```text
Какое число аренд в день необходимо,
чтобы окупаемость станции была <= 12 месяцев?
```

### Сценарий D. Сверить модель с фактом

1. Загрузить историю событий или агрегированную таблицу.
2. Подтвердить mapping данных.
3. Рассчитать фактические Flow, Stock и Rate.
4. Сравнить actual с baseline и forecast.
5. Найти источник отклонения.

Этот сценарий является целевым, но не входит в первый этап.

## 4. Архитектурное направление

### Технологический выбор

На локальном этапе остаются:

- React;
- Vite;
- TypeScript;
- `localStorage` для моделей и настроек;
- JSON для import/export.

React Router можно добавить при появлении нескольких локальных экранов. Next.js
или отдельный backend понадобятся при появлении:

- аккаунтов;
- общего доступа;
- серверных секретов;
- регулярных внешних интеграций;
- больших наборов фактических данных;
- фоновых вычислений.

### Рекомендуемые границы кода

Полную миграцию проекта на новую файловую архитектуру до начала функций делать
не нужно. Достаточно постепенно выделить headless-ядро:

```text
src/
  core/
    model/       # сущности и schemaVersion
    formula/     # parser, AST, units, validation
    graph/       # DAG и порядок вычисления
    analysis/    # scenario, sensitivity, threshold
  storage/       # localStorage, migration, import/export
  templates/
    tokberi/     # стартовая модель TokBeri
  app/           # существующий интерфейс и Canvas
```

`core` не зависит от React. Поэтому формулы можно тестировать отдельно от
интерфейса и в будущем перенести в worker или backend.

### Два графа

```text
Calculation DAG
  точные формулы
  без циклов
  исполняется движком

Influence Graph
  причинные гипотезы
  может содержать циклы
  хранит sign, weight, confidence, evidence
```

## 5. Хранение и переносимость

### Первая версия

- автосохранение с debounce;
- одна активная модель;
- последняя валидная копия;
- backup перед миграцией;
- `schemaVersion`;
- JSON export/import;
- проверка файла до замены текущей модели;
- сохранение viewport и UI-state отдельно от экономической модели.

### Позже

IndexedDB используется, когда появятся:

- большие таблицы событий;
- вложенные CSV/XLSX;
- несколько фактических датасетов;
- локальный кэш расчётных результатов.

Backend не нужен только ради сохранения локальной модели.

## 6. Этапы развития

### Phase 0. Product contract

Статус: завершён.

Результат:

- единый словарь;
- разделение типов и ролей;
- описание AST/DAG;
- границы первого этапа;
- список отложенной функциональности.

### Phase 1. TokBeri Deterministic Foundation

Статус: реализован 18 июля 2026 года.

Цель: получить полезную локальную модель одной станции и сети TokBeri.

Входит:

- сериализуемая схема модели;
- минимальный AST;
- строгий DAG;
- единицы, behavior и grain;
- TokBeri-шаблон;
- выбираемая North Star;
- baseline и сценарии;
- sensitivity и threshold;
- localStorage и JSON;
- сохранение текущего дизайна.

Подробности: [phase-1-tokberi-foundation.md](phase-1-tokberi-foundation.md).
Фактический результат: [phase-1-implementation.md](phase-1-implementation.md).

### Phase 2. Универсальный редактор моделей

Статус: реализован 19 июля 2026 года.

Цель: перестать зависеть от одного шаблона.

Входит:

- безопасный редактор формул;
- создание `Stock`, `Flow`, `Rate` и `One-off` на пустом Canvas;
- стабильные ID и пользовательские aliases;
- несколько моделей;
- Calculation-связи из формулы и графического соединения;
- Domain many-to-many;
- Visual Groups;
- произвольная North Star;
- миграция схемы v1 в v2.

Подробности: [phase-2-universal-builder.md](phase-2-universal-builder.md).
Фактический результат: [phase-2-implementation.md](phase-2-implementation.md).

Отложено до появления отдельного пользовательского сценария:

- переиспользуемый каталог определений;
- пользовательские шаблоны;
- полноценное редактирование Influence-связей.

### Phase 3. Decision Analysis

Цель: превратить калькулятор в инструмент приоритизации.

Входит:

- сравнение нескольких сценариев;
- tornado sensitivity;
- пакетный анализ нескольких абсолютных и относительных шоков;
- поиск произвольных критических значений;
- ranking драйверов;
- explanation path до North Star;
- guardrails;
- привязка инициативы или эксперимента к драйверу.

### Phase 4. Time and Stock-Flow Simulation

Цель: моделировать изменение системы по периодам.

Входит:

- календарь модели;
- начальные Stock;
- inflow и outflow;
- рекуррентные формулы;
- временные задержки;
- capacity и saturation;
- таблицы и графики actual/forecast;
- предупреждения о нарушении физических ограничений.

TokBeri-примеры:

- движение заряженных батарей;
- выданные и возвращённые устройства;
- накопленные потери;
- рост сети станций;
- денежный баланс.

### Phase 5. Actuals and Event Import

Цель: сверять модель с реальным поведением продукта.

Входит:

- CSV/JSON/XLSX import;
- canonical event schema;
- mapping wizard;
- проверка дублей и качества;
- агрегация Event -> Flow;
- state transition Event/Flow -> Stock;
- actual vs model;
- сохранение provenance.

Первый источник — выгрузка истории аренды и платежей TokBeri. Прямая
интеграция с backend появляется только после устойчивого файлового импорта.

### Phase 6. Uncertainty and Experiments

Цель: учитывать неопределённость, а не только точечные значения.

Входит:

- диапазоны и распределения;
- Monte Carlo;
- доверительные интервалы результатов;
- экспериментальные гипотезы;
- expected uplift;
- confidence и evidence;
- сравнение прогноза с результатом эксперимента.

### Phase 7. External Product

Цель: подготовить продукт для других пользователей.

Возможные функции:

- backend;
- аккаунты и команды;
- права доступа;
- облачное хранение;
- audit log;
- коннекторы;
- совместная работа;
- AI-помощник;
- публичные и коммерческие шаблоны.

Решение о Phase 7 принимается только после устойчивого личного использования.

## 7. Что намеренно не делаем сейчас

- не переезжаем на Next.js;
- не создаём backend;
- не строим универсальный BI;
- не импортируем события;
- не реализуем рекуррентную stock-flow модель;
- не делаем Monte Carlo;
- не подключаем AI-генерацию дерева;
- не моделируем франшизу как достоверный слой;
- не переписываем Canvas на стороннюю библиотеку;
- не проводим полный FSD-рефакторинг ради структуры.

## 8. Идеи из существующих решений

Используем как продуктовые ориентиры:

- Pigment — baseline и именованные сценарии;
- Lucanet xP&A — неопределённость и вероятностные значения;
- Mixpanel Metric Trees — черновик дерева из бизнес-контекста;
- Insight Maker — stock-flow и feedback loops;
- Kumu — presentation view причинных связей;
- React Flow — технические примеры cycle prevention и save/restore;
- Math.js — parser и expression tree как возможная входная технология.

У проприетарных продуктов берём общие идеи и workflow, но самостоятельно
реализуем интерфейс, тексты и алгоритмы. Open-source код используется только
после проверки лицензии и с сохранением необходимых notices.

## 9. Главные риски

| Риск | Как снижаем |
|---|---|
| Слишком сложная предметная модель | Поэтапное включение функций и понятные defaults |
| Точное число на неверных допущениях | Provenance, статус fact/assumption и validation |
| Формулы невозможно сохранить | AST вместо JavaScript closures |
| Циклы ломают вычисление | Проверка при изменении, импорте и расчёте |
| Canvas и engine оказываются связаны | Headless core без React |
| Импорт создаёт ложные факты | Preview, mapping, quality checks, подтверждение |
| Универсальность тормозит TokBeri | Сначала прикладной шаблон, затем обобщение |
| Архитектура становится enterprise раньше времени | Local-first, без backend до реальной необходимости |

## 10. Критерий правильного темпа

Каждый этап должен давать самостоятельную пользовательскую ценность.

Если новая абстракция не помогает принять решение по TokBeri и нужна только
«на будущее», она остаётся в документации до следующего этапа.
